What a coordinate does to a document

An agent is given a real repository — lab-repo/ripgrep-14.1.1, pinned — and asked to document one part of it. It reads whatever it needs. The same task runs twice: once from the task alone, once with the voice profile resolved at a coordinate appended to its system prompt. Two coordinates, four models.

Nothing here is scored. What a good user guide contains is not written down anywhere, and a rubric invented for this page would be measuring the rubric. What is shown instead is the document, the exact context that produced it, and which files the agent opened before writing — a document from a run that read nothing is a document about what the model already believed.

claude -p in the cloned tree, 60 turns maximum per document, tools on, isolation contract applied. Documents are the output; nothing is scored. Generated 2026-08-27.

The task, given to both arms

Read this repository and write a user guide, in Markdown, of roughly 800 words, for ripgrep's file-type filtering: what `--type`, `--type-not`, `--type-add` and `--type-list` do and how someone uses them. The reader searches text for a living and is not a programmer: they have a terminal open and no interest in how the tool is built. Ground every claim in what the source and the existing docs actually say.

# Voice Guide: ripgrep

The voice of ripgrep's own documentation, inferred by kapi from README.md, GUIDE.md and FAQ.md at 14.1.1, then corrected by hand.

## Tone
- Personality: knowledgeable peer, not a vendor, patient explainer who shows the reasoning, not just the answer, candid about limits and unknowns, pragmatic: gives the workaround even when the cause is unfixed, generous toward other tools and their users
- Formality: technical
- Emotion: neutral
- Humor: light
- Guidelines: Calm and matter-of-fact. Enthusiasm is reserved for genuinely good news ("Yes!") and mild exasperation is permitted at real problems ("Owch."). Answer the literal question first, in one word or one sentence when possible ("Yes. See the guide's section on configuration files."), then expand. Explain mechanism when it changes what the reader should do. Say plainly what you do not know rather than bluffing. Never promise dates or outcomes you cannot keep; state the policy and the reason instead. Treat other tools as legitimate choices; explain ripgrep's design on its own rationale. Humor is dry, rare, and arises from the situation, never from a joke inserted for effect.

## Style Rules
- Use active voice
- Sentence length: short
- Point of view: second
- Contractions: always

## Vocabulary
### Preferred Terms
- **ripgrep**: Always lowercase, including at the start of a sentence: "ripgrep is a project whose contributors are volunteers."
- **rg**: The binary name in commands and transcripts; prose says "ripgrep", shell lines say `rg`.
- **flag**: Dominant word for CLI arguments: "the -U/--multiline flag", "two flags related to colors". "options" appears only when referring to `rg --help` output.
- **-P/--pcre2**: Cite short and long forms together as a slash pair on first mention: -f/--file, -z/--search-zip, -U/--multiline.
- **Note that**: Standard caveat opener, also used parenthetically as "(Note: ...)".
- **regex engine**: Used consistently for both the default and PCRE2; "default regex engine" contrasts with "PCRE2".
- **true color**: Two words, lowercase, for RGB support: "true color support already works out of the box".
- **work around**: Verb is two words ("you can work around by simply increasing the limit"); noun is hyphenated ("The work-around above").

### Forbidden Terms
- ~~Ripgrep~~ → use **ripgrep**
- ~~blazing fast~~ → use **a timed comparison, e.g. "real 0m1.783s" vs "real 0m2.458s"**
- ~~we guarantee / we promise~~ → use **"generally", "on a best effort basis", "no promises are made"**
- ~~utilize~~ → use **use**
- ~~crate~~ → use **part of ripgrep**
- ~~struct~~ → use **leave it out**
- ~~trait~~ → use **leave it out**
- ~~API~~ → use **leave it out**
- ~~implementation~~ → use **how it works**
- ~~instantiate~~ → use **create**
- ~~glob matcher~~ → use **file name pattern**

### Competitor Terms (avoid)
- ~~ag~~ → use **The Silver Searcher**
- ~~grep~~ → use **grep**
- ~~PCRE2~~ → use **PCRE2**
- ~~cygwin~~ → use **cygwin**

## Examples
### Example 1
- Before: "RipGrep is a blazingly fast, next-generation search tool that leaves The Silver Searcher in the dust."
- After: "By default, ripgrep uses parallelism to execute its search because this makes the search much faster on most modern systems."
- Why: Lowercase product name, no superlatives, no competitor put-down, and the speed claim is tied to a stated mechanism (parallelism) rather than asserted as branding.

### Example 2
- Before: "The next release is currently scheduled for Q3, though this may slip."
- After: "ripgrep is a project whose contributors are volunteers. A release schedule adds undue stress to said volunteers. Therefore, releases are made on a best effort basis and no dates will ever be given."
- Why: States the policy and the reason behind it instead of a date. The corpus is explicit that no dates are given, and immediately follows with the honest exception for high-impact bugs.

### Example 3
- Before: "It should be noted that users may configure the man page location, and the documentation should then be accessible via standard mechanisms."
- After: "Note that the man page's documentation for options is equivalent to the output shown in rg --help. To see more condensed documentation (one line per flag), run rg -h."
- Why: Bare "Note that", concrete commands instead of abstract "standard mechanisms", and second person addressed through an imperative. Every how-to answer in the corpus lands on a runnable `$` line.

### Example 4
- Before: "Unfortunately, we are unable to provide details on PCRE2's internal behavior at this time."
- After: "Why doesn't PCRE2 do the same? This author isn't familiar with its internals, so we can't comment on it here."
- Why: Candid admission of a limit, in contractions, without corporate hedging or apology. The rhetorical question is the corpus's habitual device for advancing a technical explanation.

Filtering searches by file type

By default rg looks in every file under the directory you run it in. When you only care about one kind of file, the type filters cut the rest away. They are a naming shortcut: instead of remembering that C code lives in both .c and .h files and writing rg 'int main' -g '*.{c,h}', you write rg 'int main' -tc.

Seeing what is on offer: --type-list

ripgrep ships with a long list of predefined types, covering well known public formats. To see them:

$ rg --type-list

Each line is a type name, a colon, then the comma-separated filename patterns that belong to it:

$ rg --type-list | rg '^make:'
make: *.mak, *.mk, GNUmakefile, Gnumakefile, Makefile, gnumakefile, makefile

Some formats answer to more than one name: markdown and md appear as separate lines with identical patterns, and either one works. The list also takes into account any types you define on the same command line, so it doubles as a way to check that a definition of your own came out the way you meant.

Searching only one kind of file: --type (-t)

$ rg 'fn run' --type rust
$ rg 'fn run' -t rust
$ rg 'fn run' -trust

All three are the same command; the short form may be written with or without a space. Repeat the flag to widen the net, and the types add up:

$ rg invoice -tmd -tjson -tcsv

Once you have used -t even once, any file matching none of your chosen types is skipped. Ask for a name ripgrep does not know and it stops with unrecognized file type: ... rather than quietly searching everything.

Leaving one kind out: --type-not (-T)

The mirror image. -t means "include files of this type", -T means "exclude files of this type":

$ rg clap --type-not rust
$ rg clap -Trust

It repeats too, and it mixes freely with -t. If a single file matches both an included and an excluded type, the flag written last on the command line decides.

The special name all

--type all behaves as though you had asked for every type in --type-list at once, including any you defined yourself. The effect is that ripgrep searches only files it recognises and ignores everything else.

--type-not all is the opposite, and searches only the files ripgrep does not recognise.

Suppose you have a shell script named my-shell-script, with no extension, sitting beside my-shell-library.bash. Both -tsh and -tall find matches only in my-shell-library.bash, because the sh patterns do not cover extensionless names. -Tall finds matches only in my-shell-script.

Defining your own: --type-add

If you keep reaching for the same set of extensions, give it a name. The value is a type name, a colon, and one filename pattern:

$ rg --type-add 'web:*.html' --type-add 'web:*.css' --type-add 'web:*.js' -tweb title

Only one pattern per flag, but repeats accumulate, and a pattern can list several extensions in braces, so this is the same thing more briefly:

$ rg --type-add 'web:*.{html,css,js}' -tweb title

Your patterns are added to ripgrep's built-in ones rather than replacing them. Type names must consist only of letters and numbers, with no punctuation, and all is reserved.

You can also build a type out of types that already exist, using include followed by a comma-separated list:

$ rg --type-add 'src:include:cpp,py,md' -tsrc TODO

and then layer extra patterns on top of it:

$ rg --type-add 'src:include:cpp,py,md' --type-add 'src:*.foo' -tsrc TODO

Everything named after include: must already be defined at that point, so put your own --type-add flags before the one that includes them. (A related flag, --type-clear NAME, throws away a type's existing patterns, which is how you start from scratch rather than adding to what is there.)

Definitions last for the one command only; nothing is saved anywhere. To keep a type around, either make a shell alias:

alias rg="rg --type-add 'web:*.{html,css,js}'"

or put a line in your configuration file, the one RIPGREP_CONFIG_PATH points at:

--type-add=web:*.{html,css,js}

Three things that catch people out

  • Patterns match a file's name, not its location. *.txt works; drafts/*.txt will never match anything, because only the last part of the path is tested. To filter on where a file sits, use -g/--glob instead.
  • Files you name yourself are always searched. In rg -trust TODO notes.txt, notes.txt is searched anyway. Type filters apply to the files ripgrep goes looking for, not to paths you hand it directly.
  • Types lose to globs and to ignore files. -g patterns and the rules in .gitignore and its relatives are applied first, and a -t cannot pull back a file they have already excluded.

Filtering by file type

ripgrep can limit a search to one kind of file, or skip one kind, without you spelling out file name patterns every time. A type is a name attached to a list of file name patterns. The name md stands for *.md, *.markdown, *.mdown and a few more. The name csv stands for *.csv. You use the name, ripgrep uses the patterns.

Search one kind of file: -t/--type

$ rg 'quarterly revenue' --type md

or, more succinctly, -tmd. Same thing.

Repeat the flag to search more than one kind. The kinds add up, so this searches Markdown and plain text files and nothing else:

$ rg 'quarterly revenue' -tmd -ttxt

--type all is a special value. It searches every type ripgrep knows about, and skips everything else.

Skip one kind of file: -T/--type-not

$ rg 'quarterly revenue' --type-not log

or -Tlog. So -t means "only files of this type" and -T means "not files of this type". Repeat -T to exclude several kinds.

--type-not all is the mirror of --type all: it skips every file ripgrep recognizes and searches only the ones it doesn't. That's a quick way to find the odd files out in a folder.

You can mix the two flags. When a file matches both an included and an excluded type, the flag you wrote last wins. rg -tmd -Tmd searches nothing at all, and rg -Tmd -tmd searches your Markdown.

See what the names mean: --type-list

$ rg --type-list

You get one type per line: the name, a colon, then that type's patterns separated by commas.

md: *.markdown, *.md, *.mdown, *.mdwn, *.mdx, *.mkd, *.mkdn

The list is long, so pipe it back through ripgrep to find the line you want:

$ rg --type-list | rg '^xml:'
xml: *.dtd, *.rng, *.sch, *.xhtml, *.xjb, *.xml, *.xml.dist, *.xsd, *.xsl, *.xslt

Name a type ripgrep doesn't have and it says so instead of searching:

$ rg 'needle' -tsubtitle
rg: unrecognized file type: subtitle

Define your own: --type-add

Give the flag a name, a colon, and a pattern:

$ rg 'inaudible' --type-add 'subtitle:*.srt' -tsubtitle

Note that --type-add only defines the type. It doesn't turn it on. You still write -tsubtitle to restrict the search, and if you leave that off, the command searches everything as usual.

One pattern per flag, but you can repeat the flag, and a single pattern can cover several extensions using braces:

$ rg 'inaudible' --type-add 'subtitle:*.{srt,vtt,sub}' -tsubtitle

Adding to a name that already exists extends it rather than replacing it, so --type-add 'md:*.mmd' gives you the built-in Markdown patterns plus yours. To start a name from scratch, clear it first with --type-clear md.

You can also build a type out of types you already have. The include directive takes a comma-separated list of names:

$ rg 'deprecated' --type-add 'docs:include:md,txt,html' -tdocs

Add more patterns to it afterwards with another --type-add 'docs:*.rst'. Type names must be letters and numbers only, so no dots, dashes or spaces, and all is already taken.

Your new type shows up in rg --type-list too, since that listing takes --type-add and --type-clear into account.

Making a type stick

A type definition lasts exactly as long as the one command. ripgrep doesn't save it anywhere. To get yours every time, either make a shell alias:

alias rg="rg --type-add 'subtitle:*.{srt,vtt,sub}'"

or put it in a configuration file. Point the RIPGREP_CONFIG_PATH environment variable at a file, then write one argument per line:

# Add my 'subtitle' type.
--type-add
subtitle:*.{srt,vtt,sub}

Lines starting with # are ignored, and there's no quoting or escaping: each line goes to ripgrep exactly as written.

Two things that catch people out

Types look at file names, not at what's inside a file. A shell script named my-shell-script, with no extension at all, won't be found by -tsh, because the patterns behind sh expect an extension or a known name like .bashrc. ripgrep won't open a file to guess what it is. If a type isn't catching the files you expect, run rg --type-list and read the patterns.

Type filtering also has lower precedence than the -g/--glob flag and than the rules in any ignore files ripgrep is honoring. So -tmd won't pull in a Markdown file that an ignore file already excludes. If a search comes back with

rg: No files were searched, which means ripgrep probably applied a filter you
didn't expect.

then your filters have combined to rule out everything, and the fix is usually to drop one -t or -T and try again.
