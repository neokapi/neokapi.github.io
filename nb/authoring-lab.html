What a coordinate does to a document

An agent is given a real repository — lab-repo/ripgrep-14.1.1, pinned — and asked to document one part of it. It reads whatever it needs. The same task runs twice: once from the task alone, once with the voice profile resolved at a coordinate appended to its system prompt. Two coordinates, four models.

Nothing here is scored. What a good user guide contains is not written down anywhere, and a rubric invented for this page would be measuring the rubric. What is shown instead is the document, the exact context that produced it, and which files the agent opened before writing — a document from a run that read nothing is a document about what the model already believed.

claude -p in the cloned tree, 60 turns maximum per document, tools on, isolation contract applied. Documents are the output; nothing is scored. Generated 2026-08-28.

# Voice Guide: ripgrep

The voice of ripgrep's own documentation, inferred by kapi from README.md, GUIDE.md and FAQ.md at 14.1.1, then corrected by hand.

## Tone
- Personality: knowledgeable peer, not a vendor, patient explainer who shows the reasoning, not just the answer, candid about limits and unknowns, pragmatic: gives the workaround even when the cause is unfixed, generous toward other tools and their users
- Formality: technical
- Emotion: calm and matter-of-fact; enthusiasm reserved for genuinely good news ("Yes!"), mild exasperation permitted at real problems ("Owch.")
- Humor: light
- Guidelines: Calm and matter-of-fact. Enthusiasm is reserved for genuinely good news ("Yes!") and mild exasperation is permitted at real problems ("Owch."). Answer the literal question first, in one word or one sentence when possible ("Yes. See the guide's section on configuration files."), then expand. Explain mechanism when it changes what the reader should do. Say plainly what you do not know rather than bluffing. Never promise dates or outcomes you cannot keep; state the policy and the reason instead. Treat other tools as legitimate choices; explain ripgrep's design on its own rationale. Humor is dry, rare, and arises from the situation, never from a joke inserted for effect.

## Style Rules
- Use active voice
- Sentence length: short
- Point of view: second
- Contractions: always

## Vocabulary
### Preferred Terms
- **ripgrep**: Always lowercase, including at the start of a sentence: "ripgrep is a project whose contributors are volunteers."
- **rg**: The binary name in commands and transcripts; prose says "ripgrep", shell lines say `rg`.
- **flag**: Dominant word for CLI arguments: "the -U/--multiline flag", "two flags related to colors". "options" appears only when referring to `rg --help` output.
- **-P/--pcre2**: Cite short and long forms together as a slash pair on first mention: -f/--file, -z/--search-zip, -U/--multiline.
- **Note that**: Standard caveat opener, also used parenthetically as "(Note: ...)".
- **regex engine**: Used consistently for both the default and PCRE2; "default regex engine" contrasts with "PCRE2".
- **true color**: Two words, lowercase, for RGB support: "true color support already works out of the box".
- **work around**: Verb is two words ("you can work around by simply increasing the limit"); noun is hyphenated ("The work-around above").

### Forbidden Terms
- ~~Ripgrep~~ → use **ripgrep**: Capitalized forms (Ripgrep, RipGrep, RIPGREP) never appear; the name is lowercase in every one of ~60 occurrences.
- ~~blazing fast~~ → use **a timed comparison, e.g. "real 0m1.783s" vs "real 0m2.458s"**: Performance is always demonstrated with `time` output or `--trace` lines, never asserted.
- ~~we guarantee / we promise~~ → use **"generally", "on a best effort basis", "no promises are made"**: The release-policy entry hedges deliberately: "However, no promises are made."
- ~~utilize~~ → use **use**: "use" throughout: "ripgrep uses parallelism", "Use the --colors flag".
- ~~crate~~ → use **part of ripgrep**
- ~~struct~~ → use **leave it out**
- ~~trait~~ → use **leave it out**
- ~~API~~ → use **leave it out**
- ~~implementation~~ → use **how it works**
- ~~instantiate~~ → use **create**
- ~~glob matcher~~ → use **file name pattern**

### Competitor Terms
- ~~ag~~ → use **The Silver Searcher**: Referred to by full name with the article, and accommodated rather than attacked: an entire entry explains how to emulate its output style.
- **grep**: Named plainly and given its own entry ("Can ripgrep replace grep?"); no put-downs.
- **PCRE2**: A supported alternative engine. Tradeoffs are stated factually ("Both regex engines are quite fast") and unknowns are conceded: "Why doesn't PCRE2 do the same? This author isn't familiar with its internals."
- **cygwin**: Lowercase, described as a source of path-mangling behavior with three concrete fixes offered rather than a verdict.

Filtering by file type

A file type in ripgrep is just a name bound to a list of globs. The rust type is *.rs; markdown is *.markdown, *.md, *.mdown, *.mdwn, *.mkd, *.mkdn, *.mdx. Some types carry more than one name for the same globs, so py and python are interchangeable, as are md/markdown and bat/batch. Types save you from retyping the same glob and cover extensions you would have forgotten: the c type is *.[chH], *.[chH].in and *.cats, not just *.c.

Seeing what exists: --type-list

$ rg --type-list
...
make: *.mak, *.mk, [Gg][Nn][Uu]makefile, [Gg][Nn][Uu]makefile.am, ...
markdown: *.markdown, *.md, *.mdown, *.mdwn, *.mdx, *.mkd, *.mkdn
...

One type per line, the name, a colon, then its globs comma-delimited. Types are sorted by name and globs are sorted within a type, so rg --type-list | rg '^make:' is a reliable way to check one definition. The listing reflects any --type-add and --type-clear flags on the same command line, which makes it the way to debug a custom type. ripgrep exits with 1 if it prints no types at all.

Including and excluding: --type and --type-not

-t/--type restricts the search to a type; -T/--type-not excludes one. Both may be repeated, and the short forms can be glued to their argument:

$ rg 'fn run' --type rust        # or -t rust, or -trust
$ rg clap --type-not rust        # or -T rust, or -Trust
$ rg 'fn run' -trust -ttoml      # union of both types

Two behaviours are worth internalising. First, as soon as one -t is present, ripgrep switches to whitelist mode: anything not matching a selected type is skipped, including files with no extension. Second, when a file matches several of your type flags, the last matching flag on the command line wins. So -tfoo -Trust and -Trust -tfoo differ for a .rs file if foo covers *.rs too: the first excludes it, the second includes it. Order your flags with the narrowing you actually want at the end.

Type globs are matched against the file name, never the whole path, and never against directories. --type-add 'web:src/*.js' therefore matches nothing — push directory scoping into -g instead.

Defining your own: --type-add

--type-add takes name:glob and adds one glob at a time; repeat the flag for more. Additions extend ripgrep's built-in definitions rather than replacing them.

$ rg --type-add 'web:*.html' --type-add 'web:*.css' -tweb title
$ rg --type-add 'web:*.{html,css,js}' -tweb title       # same thing

A type name must consist only of Unicode letters or numbers; punctuation is rejected, and all is reserved. A malformed value fails with invalid definition (format is type:glob, e.g., html:*.html), and selecting a name that was never defined fails with unrecognized file type: <name>.

You can compose types with the include directive, which copies the globs of existing types into a new one:

$ rg --type-add 'src:include:cpp,py,md' -tsrc 'TODO'
$ rg --type-add 'src:include:cpp,py,md' --type-add 'src:*.foo' -tsrc 'TODO'

The referenced types must already be defined at the point the directive is processed, so put the --type-add that defines wat before the one that includes it. The companion flag --type-clear NAME drops a type's globs, which lets you redefine a built-in from scratch (--type-clear rust --type-add 'rust:*.rs'). Clearing a type and then selecting it is an error, not an empty result.

--type-add and --type-clear last exactly one invocation. Nothing is persisted. To keep a type, alias it or put it in your configuration file (RIPGREP_CONFIG_PATH), one argument per line:

--type-add
web:*.{html,css,js}

The all pseudo-type

--type all behaves as if you had passed -t for every currently defined type, which puts ripgrep in whitelist mode over everything it recognises. --type-not all is the inverse: it searches only files ripgrep does not recognise, which is a fast way to find stray extensions and extensionless scripts. Given my-shell-script and my-shell-library.bash, -tall finds only the .bash file, and -Tall only the extensionless one. all expands over the types defined at the moment the flag is read, so place --type-add before it if you want your own types included.

Where type filters sit

Type filters have the lowest precedence of ripgrep's filters. A -g/--glob match decides the file outright, ignore rules (.gitignore and friends) are consulted next, and types only afterwards. Practically: -t will not resurrect a file that .gitignore excludes — reach for -u/--no-ignore for that — and a -g '!...' beats any type selection.

Filters also apply only to files ripgrep discovers by walking. Paths you name explicitly on the command line are always searched, so rg -tpy PATTERN notes.txt still searches notes.txt.

Filtering by file type

ripgrep ships with a set of named file types. A type is a name plus a list of file name globs, and it saves you from writing -g '*.[ch]pp' -g '*.cc' -g '*.hh' for the ninth time. Four flags cover everything you'll do with them.

Search one type

-t/--type limits the search to files matching a type:

$ rg 'int main' -tc

Pass the flag again for each additional type. There's no comma list, so one type per flag:

$ rg -tpy -tjs 'def '

The name can be attached to the short flag (-trust) or given separately (--type rust). Name a type ripgrep doesn't know and it says so and stops: rg: unrecognized file type: nosuchtype.

Skip a type

-T/--type-not is the inverse. It excludes files matching a type and leaves everything else searchable:

$ rg clap -Trust

The difference matters. As soon as you use one -t, every file that doesn't match a selected type is excluded. -T on its own excludes only what you named.

Order decides

-t and -T accumulate in the order you write them, and when both cover the same file, the last one wins. So rg -trust -Trust needle searches nothing, while rg -Trust -trust needle searches your Rust files. Write the broad flag first and the exception after it.

Types are the weakest of ripgrep's filters. Both -g/--glob and any rule in a .gitignore or .ignore file take precedence, so this searches Rust files in spite of the -T:

$ rg -Trust -g '*.rs' needle

See the definitions

--type-list prints every type and its globs, one per line, name first, then a colon and a comma-delimited list. It prints and exits without searching. Pipe it back through ripgrep when you want one entry:

$ rg --type-list | rg '^make:'
make: *.mak, *.mk, [Gg][Nn][Uu]makefile, [Gg][Nn][Uu]makefile.am, ...

Run this before you guess at a name. The built-in types generally track well known public formats, and the set changes between releases.

Define your own

--type-add takes a name:glob pair and defines a new type or extends an existing one. Only one glob per flag, so either repeat the flag or use a brace alternation:

$ rg --type-add 'web:*.html' --type-add 'web:*.css' --type-add 'web:*.js' -tweb title
$ rg --type-add 'web:*.{html,css,js}' -tweb title

Both commands define a web type and then search it. Your new type shows up in rg --type-add 'web:*.{html,css,js}' --type-list alongside the built-in ones.

A type can also be built from other types with the include directive, which copies their globs in:

$ rg --type-add 'src:include:cpp,py,md' -tsrc needle

The types you include must already be defined, so a bare --type-add 'src:include:foo' fails with rg: invalid definition unless foo was defined earlier on the same command line. Adding globs to src afterwards works fine:

$ rg --type-add 'src:include:cpp,py,md' --type-add 'src:*.foo' needle

Names must consist only of Unicode letters or numbers. my-type is rejected, and all is reserved.

By default a --type-add glob joins the type's existing globs. To replace a definition instead, clear it first with --type-clear, then add:

$ rg --type-clear py --type-add 'py:*.pyx' --type-list | rg '^py:'
py: *.pyx

Making a type stick

--type-add and --type-clear apply to the current command only. Nothing is saved. If you want a type everywhere, use a shell alias:

alias rg="rg --type-add 'web:*.{html,css,js}'"

or put it in your configuration file, which ripgrep reads from the path in RIPGREP_CONFIG_PATH. Flags with values go on one line with an =, or across two lines:

# Add my 'web' type.
--type-add
web:*.{html,css,js}

What type globs match

A type glob is tested against the file name alone, never the full path. --type-add 'web:src/*.js' matches nothing. Reach for -g 'src/*.js' when you want to filter on path shape.

Type filters also don't apply to directories, so a directory named old.rs doesn't get pulled in by -trust or skipped by -Trust. Only the files inside it are judged, on their own names.

This is also why rg -tsh misses an extensionless shell script. The sh type's globs cover *.sh, .bashrc, profile and friends, but nothing that has no extension and no known name.

The special all type

--type=all behaves as if you'd passed -t for every type, including your custom ones. That's whitelist mode: ripgrep searches only files it recognizes.

--type-not=all is blacklist mode. It searches only the files no type claims, which is a quick way to find the extensionless scripts, LICENSE files and odd data your other searches keep missing.
