Your first project

A project is a committed recipe (kapi.yaml) that says which files count as content, plus the wiring that lets the coding agents in your repository reach kapi. Set it up once and every surface works the same project: the desktop app, your assistant, and the CLI.

Your project starts with an empty context, and that is the normal state on day one. It has no terms, no approved wording and no house rules, because the words a project cares about are the ones it turns out to use. The context fills as you and your agents work: an agent records what it notices, you confirm what is right, and from then on kapi check holds new writing to it.

A new project is source-only, so the loop below is about your own writing. Add languages when you want them.

1. Create the project​

  • Desktop
  • Agent (Claude)
  • CLI

Install Kapi Desktop and open it. On first open, the Connect your AI card offers whatever it detects (a Claude Code sign-in that uses your Claude subscription with no key, a local Ollama model, or a stored API key) in one click; or skip and use the demo engine.

  1. Create the project. On the home screen, click New Project, name it, and pick a source language. Or click KapiMart under sample projects to explore a realistic, pre-seeded project first: content collections, a bound voice profile and terms, five target languages, and a stocked content memory.
  2. Add content. In the Project view, add a pattern that matches your source files (for example docs/**/*.md). Kapi lists the matched files and the detected format, grouped into a collection.
  3. Read where it stands. The project home says where the project is on two axes: Content (what has been read in, what changed on disk, what is missing) and Governance (the voice profile in force, the terms bound, when it last converged). Below, the point map gives one row per point the recipe declares. Bind a voice profile and set the default point under Project Settings; the Context hub then shows what applies at any file.
  4. Bring it up to date. Bring up to date runs the project's default flow until every gated scope is shippable or parked for a person, the desktop form of kapi up. For a source-only project that means the checks. Anything a machine cannot decide lands in the Review queue; see Review & approve.

With the Kapi skill or MCP server connected, ask for the project:

Set kapi up for this project.

Claude detects the stack, runs kapi init (with --preset <stack> for a known i18n layout) and adds the content patterns it finds. What it writes is committed: a recipe, a starter voice profile, and a section in CLAUDE.md saying the voice is held by kapi, so the next session asks for it before writing. From there your prompts stay short; "check this is on brand" needs no flags, because the recipe carries them.

Install the CLI, then from your content directory:

kapi init                      # scaffold kapi.yaml + .kapi/, and wire your agents
kapi add "docs/**/*.md"        # declare the content; format auto-detected

kapi init names every file as it writes it:

Initialized kapi project "acme-docs"
  recipe: /path/to/acme-docs/kapi.yaml
  state:  /path/to/acme-docs/.kapi
  mcp:    .mcp.json (created: kapi mcp --project kapi.yaml)
  skill:  .claude/skills/kapi (created: 24 files)
  agents: /path/to/acme-docs/CLAUDE.md (voice pointer for assistants)

The last three lines are the wiring: an MCP entry that starts kapi mcp for this project, a copy of the kapi skill, and a short section in CLAUDE.md pointing an assistant at the voice. Choose the agents with --agents, or opt out with --agents none. See what kapi init wires up.

For a known stack, kapi init --preset react-i18next (or nextjs, vue-i18n, …) pre-fills the content mapping; kapi init --list-presets lists them.

The recipe is plain YAML, and what governs a source-only project sits under defaults::

kapi.yaml
version: v1
id: prj_fbqdv5uoovvpkaarpy5vnexhaq
name: acme-docs
defaults:
  source_language: en
  voice:
    pack: professional-b2b
collections:
  - path: "docs/**/*.md"

id: is the project's identity. It survives a rename, a move and a clone, and it is what joins two checkouts of one repository to one context. Keep it.

Commit the recipe and .kapi/. That directory holds the files your context is written into as you confirm things: the terms, the voice profile, the content-memory bundles and the record of where each unit stands in review. They belong in review like the rest of your source. kapi init writes a two-line ignore rule for the one part that is not, .kapi/work/, where everything derived from your files goes, plus .kapi/filters.local.json for your personal reader settings.

Every kapi command run anywhere in the tree finds the project by walking up, like git. See the project file reference for the full schema. When you want AI-backed steps, kapi models setup detects what you already have and confirms it as the default (Use with Claude).

2. Work as you normally would​

The next step is the work itself. Open your assistant in the repository and give it an ordinary writing task: fix a page, draft a section, rename a feature across the docs. Claude Code asks you to approve the project MCP server the first time, so review .mcp.json the way you would any file a repository ships.

While it works, the agent reads what applies at each file it touches and records what it notices: how you spell your own product, which word you use where two would do, and every wording you change in its draft. Each of those is recorded as a candidate with the file it came from. It ends its report with what the session recorded.

Nothing it records is in force. Checks report candidates and fail on none of them, so an agent can keep recording while you work without any risk of stopping a build.

3. Read what it recorded​

kapi context log

On a project where nothing has happened yet:

No context operations are recorded here yet.

After a session:

#3  2026-09-21T19:22:20Z  agent claude-code/s4980103f5148  propose  term "utilise", use "use"  [candidate]
  seen in docs/guide.md: "We utilise the widget to configure your account."
  Every other page in docs/ says "use".
#2  2026-09-21T19:22:20Z  agent claude-code/s4980103f5148  observe  note "The product is written \"Acme Widget\" in headings and \"the widget\" in running text."  [candidate]
  seen in docs/guide.md: "We utilise the widget to configure your account."

Every line carries who recorded it, what it is about, where it stands, and the file and sentence it was seen in. --status candidate narrows the list to what is waiting for you, and --session <id> to one agent run.

In Kapi Desktop the same log is the Recorded feed: on the home screen across every project, and in a project's Context hub for that project alone. It groups by session, and the evidence sits on the card, because a decision taken without it is a guess.

4. Confirm what is right​

kapi context confirm 3
#4  2026-09-21T19:23:01Z  person  confirm  of #3
  written to terms.json

Confirming writes the rule into the file your recipe binds, so git diff shows the decision like any other change. Change it as you confirm it with --use and --severity, or turn it down with kapi context discard 3. Either way the record stays in the log, so the same suggestion is recognisable the next time somebody makes it.

Deciding is yours. An agent observes, proposes and records corrections, and it has no verb for confirming, discarding someone else's work, reverting or widening. Growing context covers the whole set of verbs, including undoing a whole agent session in one command.

5. Check​

kapi check docs/guide.md

Before you confirmed anything, the proposal read as a note and the check passed:

  severity  rule              location                                    message
  NEUTRAL   voice.vocabulary  docs/guide.md:getting-started/next-steps/p  Proposed rule about "utilise", not yet confirmed: Every other page in docs/ says "use".
                                                                          ↳ Use "use" instead
  NEUTRAL   voice.vocabulary  docs/guide.md:getting-started/p             Proposed rule about "utilise", not yet confirmed: Every other page in docs/ says "use".
                                                                          ↳ Use "use" instead

PASS configured checks: score 100/100 · 2 finding(s) (0 critical, 0 major, 0 minor)

After confirming, the same word is a rule and bites at the severity it carries:

  severity  rule              location                                    message
  MAJOR     voice.vocabulary  docs/guide.md:getting-started/next-steps/p  Forbidden term "utilise" found in terms
                                                                          ↳ Use "use" instead
  MAJOR     voice.vocabulary  docs/guide.md:getting-started/p             Forbidden term "utilise" found in terms
                                                                          ↳ Use "use" instead

PASS configured checks: score 90/100 · 2 finding(s) (0 critical, 2 major, 0 minor)

Run kapi check with no path to check the whole project, and kapi check --ship to enforce release policy. It exits 3 when a gate is unmet, which is what makes it a CI step: see Ship gates & CI.

Repeat steps 2 to 5 as you work. Each session adds to what the project holds, and a person decided every part of it.
