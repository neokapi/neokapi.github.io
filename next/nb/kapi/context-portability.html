Moving context

A project's context includes terms, voice profiles, content memory and approval records. It lives in your local workspace, with one store per project shared by its clones and worktrees. Use these commands to exchange context as files or back it up as an archive.

VerbMovesUse it to
kapi context importa checkout's files → storebring an existing project's context in
kapi context snapshotstore → filesput a copy in git, or hand it to a clean clone
kapi context exportstore → one fileback the context up, or carry it to another machine
kapi context restoreone file → storeput a backup back, here or somewhere else

Export and restore also take --workspace, which carries every project you work on here rather than the one in front of you. See backing up every project at once.

Import and snapshot are the two directions between a directory of files and the store. Export and restore are the same two directions against a single archive.

Import and snapshot exchange context files; export and restore exchange archives.

What counts as context​

Snapshots and imports use the following files:

  • terms: the concepts and the approved word for each, per language (terms.json);
  • voice profiles: the project default and one per profile that overrides it (voice.yaml, profiles/<name>/voice.yaml);
  • content memory: the source and target pairs already produced and reviewed (memory/*.memory.json);
  • the decision record: who approved which wording, against which text (state/*.jsonl).

Content files are managed separately in git and are excluded from context backups.

What never travels​

Redaction withholds sensitive values before content reaches a model or a service, and keeps the originals in a vault on the machine that read them (.kapi/work/vault/). That vault is excluded from a snapshot and from an export, and there is no flag that puts it in either. If you move a project to another machine, the placeholders come with it and the originals do not.

The derived stores and caches under .kapi/work/ are also excluded. kapi rebuilds them from your content files.

The operation log, including observations, proposals and their evidence, remains in the local workspace. Exports contain the resulting context and unit approval records, but exclude this operation history.

Reading context in​

kapi context import
Read .kapi into the project store:
  1 concept

Import loads context files into the store shared by this project's local checkouts. Other users must import the files into their own workspaces.

Only a person can import context. kapi rejects an import attempted by an agent and reports the command for the person to run:

Error: agent claude-code/s4980103f5148 may not import context: reading a
checkout's context files puts them in force for everyone working in this
project, which a person decides: ask the person working here to run
`kapi context import`: refused by the context policy

With no path it reads the project's own .kapi/ directory. Name a directory to read another checkout's context instead:

kapi context import ../old-project/.kapi

That is the way in for a project whose context was authored as files, and the way a team hands its context to somebody starting fresh.

Each file read is recorded with its digest, so kapi context log says which files the store was built from and when:

#7  2026-09-22T07:23:03Z  person  confirm  note "content-memory bundle .kapi/memory/memory.json, 0 entries"
  seen in .kapi/memory/memory.json: "sha256:f89b91fdca8829b705701266d75fb796d11f8549e3634158adf0d23883794e7d"
#6  2026-09-22T07:23:03Z  person  confirm  note "terms bundle .kapi/terms.json, 1 concept"
  seen in .kapi/terms.json: "sha256:ef9b7f79f21235d1065dca333930ddd44147c19e3d134e640a941ef044de3c09"

Import is idempotent: concepts, entries, profiles and decisions are matched by identity. Repeating an import of unchanged files leaves the store unchanged:

Nothing to read: 2 sources already in the store at these bytes.

Unchanged files are skipped. Use --force to read them again.

Meeting a project whose context is still in files​

If a checkout contains context files but its project store is empty, commands that resolve the project print this notice to standard error:

note: this project carries context files (.kapi/memory/memory.json, .kapi/terms.json) and its store holds no context yet. They are read by `kapi context import`, and until then nothing in them is in force

kapi check carries the same line as a configuration warning, which never changes the score, the gate or the verdict:

Configuration warnings (1):

  code            location  message
  context.unread  .kapi     this project carries context files (.kapi/memory/memory.json, .kapi/terms.json) and its store holds no context yet. They are read by `kapi context import`, and until then nothing in them is in force
  Warnings are separate from findings: they never change the score, the gate or the verdict.

Kapi Desktop shows it on the project and on the workspace home, and the MCP surface carries it on the context resource, so an agent reading the project can tell you what to run. The notice stops once the store holds anything at all.

Writing context out​

kapi context snapshot --out build/context

This writes an importable snapshot to the required --out directory: terms, content memory, voice profiles and decision records. To keep snapshots in .kapi/, specify --out .kapi and adjust the directory's ignore rules before committing the files.

Snapshot files are generated. Update the project's context in its store, then create a new snapshot. Generated voice profiles include a notice to this effect.

Snapshots have the following properties:

  • Unchanged files are preserved. Repeating a snapshot without changes leaves file contents and modification times intact.
  • Round-trip stability. Importing a snapshot into an empty store and snapshotting again produces the same bytes.
  • Consistent governance. After importing a snapshot, a clean clone uses the same voice profiles, terms and rules as the exporting project.

The snapshot includes the project's current decision records, which can be committed to git for review.

A directory that already holds content-memory bundles you wrote by hand keeps them. A snapshot writes the store's own bundle beside them rather than deleting files it did not write. To get a directory holding only the snapshot, point --out at a fresh one.

Packing it into one file​

kapi context export -o context.kpz

Export creates a single archive for backup or transfer to another machine. Restore preserves the identities of the archived context records:

kapi context restore context.kpz

Restoring into a non-empty store requires an explicit merge or replacement:

kapi context restore context.kpz --merge     # read it over what is there
kapi context restore context.kpz --replace   # put it in place of what is there

--merge is idempotent, like an import: restoring the same file twice leaves the same store. --replace empties the context stores first, so what is left is the file and nothing else.

kapi rejects unsupported archive versions before restoring their contents. The error identifies the archive and the version incompatibility.

Every branch's approvals, not just the one you are on​

An export includes decisions for every branch. After restoration, each checkout uses the approvals that match its source and target text. A snapshot includes only the decision shards for the current checkout.

Backing up every project at once​

The workspace contains context for all local projects and is not tracked by git. Use --workspace to back up or restore all project context stores.

Start by seeing what you have:

kapi context export --workspace --dry-run

That writes nothing. It lists every project, what its context holds, and which of them still have a working copy on this computer. Then write the file:

kapi context export --workspace -o everything.kpz

The backup includes registered projects even if their checkouts have been deleted. It contains one .kpz archive per project, each of which can be extracted and restored separately.

Reading it back needs no checkouts at all:

kapi context restore --workspace everything.kpz

Every project comes back under the name and identity it had. Clone a repository afterwards and the first command you run there finds its context waiting.

If the destination already contains project context, specify how to handle it:

kapi context restore --workspace everything.kpz --merge     # read it over what is there
kapi context restore --workspace everything.kpz --replace   # put it in place of what is there

--replace lists the affected projects before clearing their context stores.

Workspace backups exclude redaction vaults and machine-specific checkout paths.

Which one to use​

  • Bringing an old project in, or picking up a clone that arrived with context files: import.
  • Putting a copy of the context in a pull request, or giving somebody the files their own import will read: snapshot.
  • A backup before a risky change, or moving a project between machines: export, then restore.
  • Everything you have worked on here, before a reinstall or a new laptop: export --workspace, then restore --workspace.
