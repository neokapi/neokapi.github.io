Context

kapi stores writing guidance as context: approved terms, voice profiles and previously approved wording. Writers and agents can consult it before drafting; checks use the same context to evaluate the result.

Two questions describe the model:

  • Where does this content sit? Every piece of content has a place in a context space: the product it belongs to, the channel it ships on, and any further axis the project declares for itself, such as a brand.
  • What governs that place? A point in the space binds governance: a voice profile, a terms store, and the content memory of what has been said before.

This model supports consistent writing in a single language as well as multilingual content. Language overrides refine guidance within the same profile.

The context space​

Different parts of a project can need different guidance. A framework and its companion app may have distinct voices; a marketing page and an API reference may use different registers. Two structural axes identify where guidance applies:

AxisAnswersIn the recipe
productwhich thing this belongs toa key under profiles:
channelwhich surface it ships ona channel: on the collection, as product/channel

These two axes are structural: a key under profiles: is a product, the channels a profile lists are the channels that product ships on, and a collection names its point with one channel: reference. A project that sits at a single point declares no profiles at all, and the whole of it is governed by the project defaults.

kapi.yaml
profiles:
  acme:
    channels: [docs, app, landing]
    voice:
      profile: acme

collections:
  - name: acme-docs
    channel: acme/docs
    base: web
    content:
      - path: "docs/**/*.md"
  - name: acme-landing
    channel: acme/landing
    content:
      - path: "site/pages/**/*.mdx"

This example defines one product with three channels. Add another key under profiles: for a second product. Channel names are scoped to their product, so two products can each have a docs channel with different guidance.

A collection's channel: is always written product/channel. A bare channel name is a load error, even when exactly one product declares it; the error names the qualified form to paste. A collection that binds no channel is governed by the project's default point.

Products and channels are slugs (lowercase, stable, never translated), so governance binds to an identifier that does not move when a term is reworded. A profile or a channel may carry a display concept, but resolution never looks at it. The project file reference covers the field shapes in full.

Declared axes​

Beyond product and channel, a project can name the further dimensions its content varies along. These axes are declared, under defaults.coordinates, and every collection inherits them. A collection that sits elsewhere on one axis overrides that axis alone with its own coordinates: and keeps the rest. The most specific value wins, per axis.

kapi.yaml
defaults:
  coordinates:
    brand: acme

collections:
  - name: acme-docs
    channel: acme/docs
    coordinates:
      mode: how-to
    content:
      - path: "docs/**/*.md"

Two axes have a conventional spelling. brand is the brand a point sits under, coarser than product: a workspace has brands, a brand has products, a product ships channels. mode is the kind of document at the point, in the sense the Diátaxis scheme means: tutorial, how-to, reference or explanation. The mode axis allows different guidance for tutorials and architecture notes. The coordinate map is open, and a project that splits its content some other way declares the axis it needs.

Product and channel are never written under coordinates:. They are derived from a collection's channel:, and a recipe that declares one there is rejected at load, so the point a recipe computes and the point it states cannot disagree.

What governs a point​

Three stores hold the context. They live in your workspace, one set per project, and the recipe says which of them applies where by naming it:

StoreHoldsBound by
voice profiletone, register, style measures and pattern rulesdefaults.voice or a profile's voice:, by profile name
termsthe approved word for each concept, per language, and every word to avoidthe project's own terms, or a profile's termstore:
content memorysource/target pairs already produced and reviewedthe project's own content memory

A profile binds a voice and a set of terms to its whole product; the collection's channel then refines the voice, selecting a channel-specific override inside the bound profile when one exists. A point that declares no override of its own falls back to the project default, the right answer for a voice that reads the same everywhere.

Two recipe keys sit beside these bindings. A collection with no target language can say so with source_only: true, so a run reads and checks it and writes nothing back; the project file reference covers it. And every wording rule ("write this, not that") is a term: it has the same shape as the term_rules: a check or a translation step takes, a term, its replacement and whether a violation fails the check. A voice file may carry such rules beside the voice under terms:, as the starter packs do, and kapi context import moves them into the project's terms. The voice profile reference lists the fields.

Where a profile's context lives​

All of it is in the project's stores, under one profile id per voice. A profile that overrides the voice names the id it uses; one that overrides the terms names a terms store with termstore:. A profile that names neither is governed by the project defaults.

kapi.yaml
profiles:
  acme-labs:
    channels: [docs]
    voice:
      profile: acme-labs      # this product's voice
    termstore: labs-terms     # this product's terms, a store by name

Content memory and the decision record belong to the project rather than to a profile. Memory entries and approvals are associated with content units. See the project store for what each store holds.

kapi context snapshot writes all of it back out as files, one directory per profile under profiles/ in the directory you name, and kapi context import reads that shape back in.

How a point resolves​

Governance resolves from the broadest binding toward the most specific, and the most specific one that exists wins:

A collection's point resolves up the ladder; an unbound collection stops at rung 1.

The rungs behave differently:

  • Rung 2 selects a store. The profile's voice: wins as written; failing that, the profile the store holds under the profile's own name; failing that, defaults.voice. Terms are one rung: the profile's termstore:, else the project's own terms.
  • Rung 3 refines what rung 2 selected. A channel entry inside the bound voice profile replaces the tone, the style, or both, so a landing-page register is authored once beside the voice it varies rather than duplicated into a file per product-and-channel pair. A channel the profile has no entry for takes the base voice.

Terms apply to every channel. The words a product will and will not use are the same on every surface it ships on, which is why rung 3 moves the register and leaves the terms alone.

kapi validates governance declarations when loading the recipe. It rejects unknown channels, unqualified channel references, invalid slugs and voice bindings that name two sources.

Governance can have a lifetime​

A profile can declare from when until when it is the one in force. The bounds are a date or an RFC3339 instant, and the window is half-open: valid_from is inclusive, valid_to exclusive, so a valid_to date excludes that whole day.

kapi.yaml
profiles:
  acme-relaunch:
    channels: [landing]
    voice:
      profile: acme-relaunch
    valid_from: 2026-09-01
    valid_to: 2026-12-01

A profile outside its window stops governing. Resolution falls through to the next binding (the collection's channel, then the project default) exactly as if the expired one were not declared, so a seasonal voice applies only within its configured dates. The same instant governs a whole run, so a long convergence cannot cross a boundary halfway through.

The switch is always reported. The first time a run, a check or a push resolves through a lapsed profile it says so:

governance: profile "acme-relaunch" expired 2026-12-01; governing with the project default

kapi context search reads every bounded profile against the current time and labels it active, upcoming or expired, so a writer can see that the guidance they are about to follow has a start or an end date before it lapses.

The same half-open window scopes an individual term, which is what lets a vocabulary survive a rename: recognise the old name until March is a different instruction from never use it, and a context answer distinguishes them.

Two questions​

Because the stores govern one point together, you do not ask them one at a time. You ask by location or by content, and kapi reads whichever stores hold the answer.

QuestionAskOver MCP
what applies here?kapi context <path>read context://<path>
what do we know about this?kapi context search <query>call context_search

What applies here​

Point kapi context at a file before you write it. The answer is a short brief: the voice in force, one list of the words to use and to avoid there, and what has been suggested but not yet established. It is written to be read by a person or dropped into a model's context.

kapi context docs/billing.md
# Writing docs/billing.md

Voice: Fernwell. Plain, second person, for studio owners who are not accountants. Short sentences.

Say this, not that:
- Fernwell Ledger, not "the Ledger": The product. Always the full name in prose.
- person, not "seat"

Suggested, not yet established:
- Quickcast is the forecast feature, always one word, capital Q (claude-code, seen in README.md)

Nothing else is recorded for this file. If you notice a name or spelling the project keeps to, record it with context_observe (or `kapi context observe`).

The word list merges the terms bound at the point, the rules established across the workspace and the terms of a starter pack bound as the voice, so a rule held in two places is one line naming both. The voice shows only the fields the profile sets. kapi voice guide <path> prints the full profile.

Context queries, runs, checks and pushes use the same governance resolver. The result includes content-item channel overrides and profile validity windows. The answer is for the file's own content. An item that declares a file for its comments alone governs only those comments, so the answer comes from the next item that claims the file, or from the project's default point.

With no file in hand (an ad-hoc draft, a starter pack), name a profile instead:

kapi context --profile marketing

--explain adds how the answer was reached: the point the file sits at, the recipe line that bound the voice, the project and workspace revision that answered, and every note. --json gives all of it as data. Over MCP the two addresses are resources rather than tools, because reading what already applies at a place takes no arguments; context://docs/billing.md is the same text, and context://docs/billing.md?format=json is the same document --json prints.

What do we know about this​

The other question takes a word or a phrase and asks it of every store the project binds:

kapi context search "sign-in"

One question reaches every store bound at the point.

Results include preferred terms, discouraged terms and their replacements, and previously approved wording. They are grouped by kind and identify any store that could not be read.

Results also show term usage counts from the context graph built by the last kapi up. A newly added term has no recorded uses until the next extraction. The desktop explorer and concept page use the same counts.

Approved wording that contains a discouraged term is flagged. Use --locale to restrict terms to one language and --json for structured output matching the MCP tool response.

An answer with nothing in it​

A project with no recorded context returns an explicit empty result:

# Writing docs/billing.md

Nothing is recorded for this file yet. Write as the surrounding files do.

While you read, record the names and spellings this project keeps to, such as a product or feature name, with context_observe (or `kapi context observe`).

The response invites an agent to record observations as suggestions (Growing context). If the checkout contains unimported context files, it instead starts with a notice asking a person to run kapi context import.

The JSON carries the same fact as a coverage value, so a script or an assistant can act on it. It counts what is in force at the point: the voice profile, the terms bound there, and the rules you have confirmed (Growing context). A search counts the terms it matched and the prior wording it found.

coverageWhat stood behind the answer
coveredtwo or more of them
thinone of them, or candidates alone
emptynothing

Unreviewed candidates raise coverage from empty to thin, but cannot produce a covered result. The response reports the number awaiting review in kapi context log.

coverage describes the answer rather than the project, so a search for a word nobody here has written about is empty however much the project holds elsewhere.

Every answer says what it read​

Each answer records the project it came from, the revision of your workspace it was read at, and whether the content kapi holds still matches the files on disk. --explain prints them:

Read from project `prj_7k2n…` at workspace revision 41, content current.

In the JSON the same three sit under provenance. Two answers carrying one revision were read from one state of your context, which is what lets you compare them. A stale answer means files changed since kapi last read them, so counts taken over your content describe the files as they were; kapi up reads them again.

Context throughout the writing process​

Use context before, during and after writing:

  • Before: the voice guide and the approved terms go into a writer's context (a person's, or an agent's), to guide the draft. The agent skill injects them automatically; kapi context <path> and context_search fetch them on demand.
  • During: agents can record observations and corrections as suggestions for review. See Growing context.
  • After: kapi check scores the result block by block against the same stores, with an exit code, so the rules hold in the editing loop and again in CI with no assistant present.

A rule an agent proposes is a candidate. It is reported by checks, it fails none of them, and it binds when you confirm it. Confirming writes it into the project's store through the same route kapi apply takes, and records the decision beside the evidence, so kapi context log is the review surface for the rules. Where the decisions are already made, kapi apply lands them as typed change-set entries directly.

One more axis: language​

Adding target_languages to the recipe adds no governance axis. A translated block sits at the point its source sits at, and the same profile governs it: the voice bound at acme/landing is the voice its Norwegian landing page is written in, and the terms bound at acme/docs are the terms its German documentation uses.

What a language adds is an override inside the voice profile, next to the channel overrides: a locales: entry carries the formality, the point of view, the cultural notes and the examples that hold for that language only. Terms carry their renderings per language. So the thing you author for one language is the thing that governs every other, and the loop that keeps the languages in step is convergence.
