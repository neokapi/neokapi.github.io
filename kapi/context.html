Context

Getting content right is not only about the words in the file. It is about what those words are supposed to be — what this project calls a thing, which wording it has already approved, what it will not say. kapi keeps that knowledge as context: the standing record a person or an AI agent consults before writing and is checked against after.

Two questions describe the model:

  • Where does this content sit? Every piece of content has a place in a two-axis space — the product it belongs to and the channel it ships on.
  • What governs that place? A point in the space binds governance: a voice profile, a terms store, and the content memory of what has been said before.

The context space​

Content is written for a point, not for a project. A repository that holds both a framework and the app built on it is not one voice; a marketing page and an API reference are not one register. The two axes name the point:

AxisAnswersIn the recipe
productwhich thing this belongs toa key under profiles:
channelwhich surface it ships ona channel: on the collection, as product/channel

The space is structural, not declared: a key under profiles: is a product, the channels a profile lists are the channels that product ships on, and a collection names its point with one channel: reference. A project that sits at a single point declares no profiles at all — the whole of it is governed by the project defaults.

kapi.yaml
profiles:
  console:
    channels: [app, docs]
    voice: .kapi/profiles/console/voice.yaml
  sdk:
    channels: [docs, cli]
    voice: .kapi/voice.yaml

collections:
  - name: console-app
    channel: console/app
    content:
      - path: "console/i18n/**/*.kbf.json"

Products and channels are slugs — lowercase, stable, never translated — so governance binds to an identifier that does not move when a term is reworded. A profile or a channel may carry a display concept, but resolution never looks at it. The project file reference covers the field shapes in full.

What governs a point​

Three stores hold the context, and all three are committed to git and versioned like code — the recipe binds them, git diff reviews changes to them:

StoreHoldsBound by
voice profiletone, register, preferred and forbidden vocabularydefaults.voice or a profile's voice:
termsthe approved word for each concept, per languagedefaults.terms_source or a profile's terms:
content memorysource/target pairs already produced and revieweddefaults.memory_source

A profile binds a voice and a vocabulary to its whole product; the collection's channel then refines the voice, selecting a channel-specific override inside the bound profile when one exists. A point that declares no override of its own falls back to the project default — the right answer for a voice that reads the same everywhere.

One question, every store​

Because the stores govern one point together, you do not ask them one at a time. kapi context search — and the context_search tool over MCP — asks a single question across every store the project binds:

kapi context search "sign-in"

One question reaches every store bound at the point.

The answer says what the project calls the thing, whether it is discouraged and what to say instead, and any wording already approved — grouped by kind, and naming any store it could not reach. You do not have to know which store holds the answer, which is the whole point: asking before you write is the cheap route, and learning the same fact from a failing check afterwards is not.

Two directions around the writer​

Context works on both sides of the moment content is written:

  • Before — the voice guide and the approved terms go into a writer's context (a person's, or an agent's), so a draft starts compliant rather than being corrected into compliance. The agent skill injects them automatically; context_search fetches them on demand.
  • After — kapi check scores the result block by block against the same stores, with an exit code, so the rules hold in the editing loop and again in CI with no assistant present.

Rules an agent proposes — a new forbidden term, a newly approved translation — land through kapi apply as typed change-set entries in the committed stores, so the review surface for the rules is git diff, exactly as for code.
