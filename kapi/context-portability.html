Moving context

A project's context is the terms it has agreed on, the voice profiles that govern how it writes, the wording it has already approved, and the record of who approved what. It lives in two places at once: as files under .kapi/ that git tracks, and in the project store that every command reads.

Four verbs move it between those places, and out of the project altogether.

VerbMovesUse it to
kapi context importfiles → storebring an existing project's context in
kapi context snapshotstore → filesput the context in git, or hand it to a clean clone
kapi context exportstore → one fileback the context up, or carry it to another machine
kapi context restoreone file → storeput a backup back, here or somewhere else

Export and restore also take --workspace, which carries every project you work on here rather than the one in front of you. See backing up every project at once.

Import and snapshot are the two directions between the files and the store. Export and restore are the same two directions against a single archive.

The same context in three shapes. Nothing is lost on any leg.

What counts as context​

The same four things everywhere, in the form each one is committed in:

  • terms: the concepts and the approved word for each, per language (.kapi/terms.json);
  • voice profiles: the project default and one per profile that overrides it (.kapi/voice.yaml, .kapi/profiles/<name>/voice.yaml);
  • content memory: the source and target pairs already produced and reviewed (.kapi/memory/*.memory.json);
  • the decision record: who approved which wording, against which text (.kapi/state/*.jsonl).

Your content files are not in it. They are in git, and a project's context is about them rather than a copy of them.

What never travels​

Redaction withholds sensitive values before content reaches a model or a service, and keeps the originals in a vault on the machine that read them (.kapi/work/vault/). That vault is excluded from a snapshot and from an export, and there is no flag that puts it in either. If you move a project to another machine, the placeholders come with it and the originals do not.

The rest of .kapi/work/ is excluded too. It is the store itself and the caches kapi rebuilds, none of which is context.

Reading context in​

kapi context import

With no path it reads the project's own .kapi/ directory. That is the same read kapi up performs on every run, so you rarely need to ask for it; ask when you want the store current before running something else, or when you have just edited a committed file by hand.

Name a directory to read another checkout's context instead:

kapi context import ../old-project/.kapi

This is the way in for a project whose context was authored before it had a store, and the way a team keeps some of its context in git while the rest is edited through kapi.

Reading twice changes nothing. Every concept, entry, profile and decision is matched by the identity it already carries, so a second read finds the store already holding what the file says. A file whose bytes have not moved since the last read is skipped; --force reads it anyway.

Writing context out​

kapi context snapshot --out build/context

This writes the .kapi/ layout: terms.json, memory/memory.json, each voice profile at the path the recipe binds it from, and the decision record's shards. With no --out it writes the project's own .kapi/ directory.

The files it writes are generated. Each voice profile it creates says so at the top of itself. Change the project's context and snapshot again rather than editing them, the way you would with any other generated artifact.

Three properties make a snapshot usable as a reviewed artifact:

  • It does not churn. A snapshot with nothing to say writes nothing, so it leaves no diff and no modification times behind.
  • It round-trips. Read a snapshot into a project with no store and snapshot again, and you get the same bytes.
  • A clean clone governs the same way. A checkout holding a snapshot and no store resolves the same voice, the same terms and the same rules the project that wrote the snapshot resolves.

A snapshot writes the project's committed record first, the same write kapi commit makes, so the record in the snapshot is the project's record rather than a copy that has already drifted from it.

A directory that already holds content-memory bundles you wrote by hand keeps them. A snapshot writes the store's own bundle beside them rather than deleting files it did not write. To get a directory holding only the snapshot, point --out at a fresh one.

Packing it into one file​

kapi context export -o context.kpz

One file holding everything above. It is the backup a store that holds reviewed work needs, and the way to carry a project's context to another machine. Nothing is flattened on the way: every part travels in the form kapi reads it back from, so a restore puts it into a store with the identities it left with.

kapi context restore context.kpz

Restoring into a project whose store already holds context stops and asks which you meant:

kapi context restore context.kpz --merge     # read it over what is there
kapi context restore context.kpz --replace   # put it in place of what is there

--merge is idempotent, like an import: restoring the same file twice leaves the same store. --replace empties the context stores first, so what is left is the file and nothing else.

A file written by a later kapi than the one reading it is refused by name, with the version that could not read it, rather than read halfway.

Backing up every project at once​

Your projects share one place for their context on this computer, and git does not track it. Losing it loses the terms, the voice profiles, the approved wording and the recorded decisions of every project you work on here. Two flags back up the whole of it.

Start by seeing what you have:

kapi context export --workspace --dry-run

That writes nothing. It lists every project, what its context holds, and which of them still have a working copy on this computer. Then write the file:

kapi context export --workspace -o everything.kpz

A project travels whether or not you still have it checked out here, which is the point: a repository you deleted a year ago keeps the terms and approvals it earned, and they come back with it. Each project inside the file is a complete context file of its own, so unzipping the backup gives you one .kpz per project that kapi context restore reads on its own.

Reading it back needs no checkouts at all:

kapi context restore --workspace everything.kpz

Every project comes back under the name and identity it had. Clone a repository afterwards and the first command you run there finds its context waiting.

A computer that already has projects of its own stops and asks which you meant, the same way a single project does:

kapi context restore --workspace everything.kpz --merge     # read it over what is there
kapi context restore --workspace everything.kpz --replace   # put it in place of what is there

--replace lists every project whose context it is about to empty before it empties any of them, so a backup aimed at the wrong computer is something you read rather than something you discover.

Withheld originals are not in a workspace backup either, and neither are the directories your projects live in. Those name folders on one computer and mean nothing on the next.

Which one to use​

  • Bringing an old project in, or keeping part of your context authored in git: import.
  • Putting the context in a pull request, or giving a clean clone what it needs to converge: snapshot.
  • A backup before a risky change, or moving a project between machines: export, then restore.
  • Everything you have worked on here, before a reinstall or a new laptop: export --workspace, then restore --workspace.
